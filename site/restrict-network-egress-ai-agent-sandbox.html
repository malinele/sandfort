How to restrict network egress from an AI agent sandbox

Put the sandbox on a network that can reach only a forward proxy, and let the proxy decide which hostnames, domains and address ranges each sandbox may connect to. An allowlist stops connections to unlisted destinations, to internal addresses and to the cloud metadata service, but it does not stop data from leaving through a destination you allowed. The network is open unless you ask for an allowlist or a full block.

Published: 2026-11-24Updated: 2026-11-27Sandfort 0.1.0

Code that an agent writes can read whatever the sandbox can read: mounted volumes, a cloned repository, its environment. With open outbound internet it can send that anywhere. Inside your own network it can also try internal services and the metadata address. A narrow goal looks like this: the sandbox may reach the model provider, a package index if it installs packages, and nothing else.

This article walks through how Sandfort implements that control, why it picked a proxy over the alternatives, and where the control ends. The reasoning about firewall rules, DNS filters and proxies carries over to most sandbox setups, including one you build yourself. The host rules shown here are specific to Linux Docker hosts with the iptables backend.

The 2026-11-27 revision brings the article in line with egress v2: address-range entries, changing the list on a running sandbox, jobs mode and a DNS sink for the container tier. A sandbox created without egress_allowlist and without block_all has open access to the public internet. That is the default (docs/security.md, Network), and an operator can change it with SANDFORT_DEFAULT_BLOCK_NETWORK or SANDFORT_ENFORCE_BLOCK_NETWORK.

Why not a firewall rule or a DNS filter?

The design document (docs/egress-allowlist-design.md) compared three mechanisms before choosing one.

  • Per-sandbox firewall rules by IP. Operators think in names, rules work on addresses. Large providers change addresses often and share CDN addresses with unrelated tenants, so a resolved set goes stale or admits more than intended. The addresses a name resolves to at create time can differ from the ones the sandbox resolves later. Every create, stop and delete edits shared tables, and crash cleanup needs the reconciler to understand firewall state. Not chosen.
  • A DNS-filtering resolver. It answers only allowlisted names. Code can connect to an IP address directly, hard-code an address or ship its own resolver. It controls discovery, not reachability. Dismissed as a control.
  • A forward proxy with per-sandbox credentials. The sandbox network admits only the proxy. The proxy reads the requested hostname or IP address, checks it against that sandbox's list and relays or refuses. Software that ignores the proxy variables can reach nothing but the proxy endpoint, so the control fails closed on a host where deploy/host-setup.sh has run. Chosen.

How does traffic get forced through the proxy?

Two pieces work together. Neither is enough alone.

  • A separate bridge. A sandbox created with an allowlist joins sf-egress-net (interface sf-br1) instead of the default sf-net. deploy/host-setup.sh installs the SANDFORT-EGRESS-PROXY chain for that bridge, which rejects everything except replies and the proxy endpoint. A second chain, SANDFORT-HOST-GUARD-PROXY, allows one new connection to the host, tcp to the proxy address and port, plus udp and tcp port 53 to the sink address when a DNS sink is configured. This network rule is what blocks direct IP connections, so the design calls it load-bearing.
  • Proxy variables with a signed token. The server sets http_proxy, https_proxy, HTTP_PROXY and HTTPS_PROXY in the sandbox environment (src/sandfort/egress/env.py). The proxy URL carries the sandbox id and an HMAC-signed egress token as userinfo, which clients send as Proxy-Authorization. A current token holds the sandbox id and a credential epoch, not the list. The proxy reads the list for that sandbox from an internal route on the API (SANDFORT_EGRESS_POLICY_URL) and uses a fetched policy for 5 seconds by default (src/sandfort/egress/tokens_v2.py, src/sandfort/egress/policy_client.py). A reset raises the epoch, which makes the previous container’s token stop working.

The control fails closed at create time too. If SANDFORT_EGRESS_PROXY_ADDRESS or SANDFORT_EGRESS_SECRET is unset on the API, an allowlisted create is refused with 409 and never runs with open egress. If sf-egress-net is missing on a node, Docker rejects the create (docs/operations.md, "Egress proxy"). The policy route is off by default. Without it, or without the secret, the proxy treats every policy as unavailable and refuses the connection.

What does the proxy check on each connection?

The proxy is a small asyncio process, one per node (src/sandfort/egress/proxy.py). For every connection it first takes a global slot and a per-source slot before authentication (503 or 429 when full), then runs these checks in order. It answers the first failed check with an error status and closes the connection. A connection that errors or times out is dropped without a status.

The address check is what stops an allowlisted name from becoming a path into your network. A tenant who controls DNS for an allowed name could point it at 10.0.0.5 or at the node itself. The proxy refuses loopback, link-local and RFC 1918 ranges by default (SANDFORT_EGRESS_DENIED_CIDRS), always adds the node's own interface addresses, always refuses the IPv6 translation prefixes (NAT64, 6to4 and Teredo, src/sandfort/egress/rules.py), and also runs check_address from src/sandfort/webhooks/ssrf.py, which rejects metadata addresses and anything not publicly routable.

Each decision is logged to stderr with the sandbox id, target host and policy generation, never the credential. A name that matched no rule is logged only as its length and a short keyed digest, never as text (src/sandfort/egress/logname.py). The log line for a refusal is rate limited: the first refusal per sandbox and reason is written at once, then at most one line per 60 seconds that ends with a suppressed= count. The client still gets every refusal. Idle tunnels close after 300 seconds by default.

The proxy can also count its answers. This is opt-in. When SANDFORT_EGRESS_METRICS_LISTEN names a loopback IPv4 address and port, the proxy serves two Prometheus counters there, sandfort_egress_decisions_total (labels decision, status and reason_class) and sandfort_egress_connection_cap_hits_total (label scope). No sandbox id, org id or host name is a label. Unset, nothing listens. Any other address, IPv6, the proxy port and port 53 are refused at startup. The counters reset when the proxy restarts, and proxy decisions are not audit rows (CHANGELOG.md, round 97, docs/operations.md).

How do you create a sandbox with an allowlist?

Pass egress_allowlist at create time. With the Python SDK:

python
from sandfort_sdk import Client

client = Client(base_url="http://127.0.0.1:8000", api_key="sf_...")
sbx = client.create_sandbox(
    name="pip-only",
    snapshot="python:3.12-slim",
    egress_allowlist=["pypi.org", "files.pythonhosted.org"],
    isolation="gvisor",
    wait=True,
)

This create needs the egress proxy from the section below, and a server that offers the gvisor tier (client.isolation() lists them). Drop isolation to use the server default.

The CLI takes --egress HOST, repeatable, on sandfort sandbox create. The TypeScript SDK takes egressAllowlist on createSandbox. The rules for entries, from the design document, src/sandfort/domain/sandbox.py (check_egress_allowlist) and src/sandfort/egress/proxy_limits.py (host_allowed):

  • Three entry forms in one list. A host name, a leading-dot domain or a CIDR range. A host entry carries no scheme, port, path or IP literal. At most 16 entries of all forms by default (SANDFORT_EGRESS_ALLOWLIST_MAX_ENTRIES).
  • Leading dot for a domain. .example.com admits example.com and every subdomain. example.com admits that name only. There are no other wildcards, patterns or globs.
  • CIDR for address ranges. An entry such as 140.82.112.0/20 admits a connection whose target is an IP literal inside the range. It never admits a host name. The entry must be canonical with no host bits set, have a prefix of at least /8 for IPv4 or /32 for IPv6, and be entirely global. Private, shared, link-local, multicast, reserved, documentation and translation ranges are rejected, and so is any range that overlaps the server’s denied networks. An IP address is reachable only through a CIDR entry (src/sandfort/domain/egress_entries.py, docs/connect-guide.md). A CIDR entry admits everything at those addresses, including every tenant of a shared range.
  • List every host the tool touches. For pip installing from PyPI that is the index host, pypi.org, and the file download host, files.pythonhosted.org, as in the example. Direct URLs, VCS installs and other indexes need their own hosts.
  • An empty list means no network. [] creates the sandbox with block_all set. Leaving the field out keeps the deployment’s default egress. An operator can make a network block the default, or enforce it, and with the enforced setting a create that names an allowlist is refused with 403.
  • No combination with a full block. block_all together with a non-empty allowlist is rejected as contradictory.

Can you change the list on a running sandbox?

Yes, for a sandbox that was created with a non-empty allowlist. Send PATCH /v1/sandboxes/{id} with egress_allowlist. The Python SDK has set_egress_allowlist(sandbox_id, entries) and the TypeScript SDK takes egressAllowlist on updateSandbox. The list is validated like a create, replaces the stored one and raises the sandbox’s policy generation by one. It writes to the database only, so it also works while the sandbox is stopped. An identical list is a no-op (src/sandfort/services/egress_update.py, docs/egress-v2-design.md section 3.4).

  • Timing. With the defaults, new connections follow the change within about 5 seconds, and open tunnels to destinations the new list no longer admits are closed within about 7 seconds (SANDFORT_EGRESS_POLICY_CACHE_S 5, SANDFORT_EGRESS_POLICY_TIMEOUT_S 2). The 200 from the API means the policy is stored, not that every proxy has applied it. If a proxy cannot reach the policy route, it refuses new connections once its cached policy is stale, and closes open tunnels after 60 seconds without a successful refresh (SANDFORT_EGRESS_POLICY_MAX_STALE_S). Data sent through a tunnel before it closes is gone.
  • An empty list. A PATCH to [] blocks every new connection and closes open tunnels. The sandbox stays on the egress network.
  • No removal. null is refused with 422. A sandbox cannot go from a list back to open egress. Create a new sandbox for that.
  • Where it does not apply. A sandbox created without an allowlist is on the open network, and one created with [] has no network. Both answer 409 to a PATCH, so create a new sandbox. A sandbox created before egress v2, with a legacy credential (policy generation 0), also answers 409 until you reset it. A reset mints a current credential.
  • Operator policy. With SANDFORT_ENFORCE_BLOCK_NETWORK set, a PATCH that carries the field is refused with 403.

How do you run the proxy?

From docs/operations.md. Run it where sandboxes can reach it, with the same secret the API uses:

bash
SANDFORT_EGRESS_SECRET=<same secret as the api> \
SANDFORT_EGRESS_POLICY_URL=<base url of an api on the private network> \
SANDFORT_EGRESS_LISTEN_HOST=0.0.0.0 SANDFORT_EGRESS_LISTEN_PORT=3128 \
python -m sandfort.egress.proxy

The policy URL names an API instance on the private network. Set SANDFORT_EGRESS_POLICY_ROUTE_ENABLED=true on exactly the API instances it points at, and leave it unset on any API that faces beyond the private network. Without the policy URL, current credentials get 503 and no sandbox created after egress v2 has egress. Then point the API at the proxy with SANDFORT_EGRESS_PROXY_ADDRESS (host:port) and run deploy/host-setup.sh as root on each Docker host. Give it the same endpoint with SF_EGRESS_PROXY=host:port. If you leave SF_EGRESS_PROXY unset, the script derives the endpoint from SANDFORT_EGRESS_PROXY_ADDRESS in its env file, else from the gateway of sf-egress-net. The port must match in all three places, or sandboxes cannot reach the proxy. sudo sh deploy/host-setup.sh --dry-run prints the iptables commands without applying them.

At startup the proxy logs its denied networks and a message egress allowed ports: followed by the port list, for example egress allowed ports: 443,80. Read it after every deploy. A proxy left running from an older image keeps its old rules.

Jobs mode and multi-node. An allowlisted create is accepted in jobs mode, which multi-node placement requires. The node that owns the sandbox mints the egress token before it creates the container, with its own proxy address and secret. Placement considers only nodes whose heartbeat reports the egress stack, meaning a proxy address, the secret and a policy URL in that process’s environment. When no node qualifies the create is refused with 409, and a node without egress settings fails the job with the error code egress_unavailable and creates no container. Every node needs the same secret, a proxy, the DNS sink below, deploy/host-setup.sh, a policy URL reachable over the private network and synchronized clocks (docs/operations.md, "Egress in jobs mode and multi-node").

DNS sink. To close the DNS side channel on the container tier, run the proxy with SANDFORT_EGRESS_DNS_SINK_LISTEN and set SANDFORT_EGRESS_DNS_SINK_ADDRESS on the API to the same IPv4 address. Port 53 is privileged, so the proxy needs root or CAP_NET_BIND_SERVICE. Both settings are unset by default, and unset keeps the old behavior. The next section says what the sink does.

What does an allowlist not stop?

This part matters more than the mechanism. Each item comes from the design document or the per-tier notes in docs/isolation-tiers.md.

  • Exfiltration through an allowed host. TLS is tunneled, so the proxy sees the hostname and nothing else. It cannot see paths, bodies or which account the request uses. Allowing a host allows everything that host accepts, including an account an attacker controls on the same service.
  • DNS on the container tier, when no sink is set. A container-tier sandbox on the egress network gets its names from Docker’s embedded resolver, which forwards to the host’s upstream servers, so a looked-up name can carry data even though the connection is refused. With SANDFORT_EGRESS_DNS_SINK_ADDRESS set, the API gives those containers the proxy’s DNS sink as their only DNS server. The sink answers every query with REFUSED, forwards nothing and never logs a queried name, so only the proxy resolves names and direct lookups fail. On the hosted beta (an invite-only evaluation instance with no SLA) the sink has been on since the API restart at 2026-11-25T08:12:30Z. A sandbox created before that, or before you set the sink on your own host, keeps the old resolvers until it is reset or recreated. On gvisor and microvm direct lookups fail at once and the sink does not apply. The sink depends on how Docker forwards DNS and does not cover a sandbox on the open network. The proxy itself still resolves any name the allowlist admits, so a domain entry over a zone where others can create names lets code put data into the name it connects to. Cover only zones you trust (docs/isolation-tiers.md, "Network modes and DNS, per tier", docs/egress-v2-design.md sections 6 and 11).
  • The credential is readable. The proxy variables, including the token, are visible to code in the sandbox. The token works only through the proxy and only for that sandbox’s current list, so the exposure stays within that list. A reset or a delete revokes it.
  • No credential injection. The proxy does not add credentials to requests for you. Any credential you send into a sandbox, such as a git token or an API key in its environment, is visible to the code running there, and the proxy does not change that (docs/security.md, Git credentials).
  • Tunnels that outlive a change. A change takes effect within seconds, not instantly. A connection can carry data until the proxy closes it.
  • Content and volume. There is no packet inspection, no TLS interception and no limit on how much goes to an allowed destination.
  • Anything without the host rules. The server cannot read iptables rules, but in prod it tests them at startup. Its egress probe starts a short-lived canary container on each managed network and tries to reach the metadata address, the bridge gateway’s SSH port, a private address and, on sf-egress-net, one public address. Startup is refused if any connect succeeds. SANDFORT_EGRESS_ACKNOWLEDGED=true turns that refusal into a logged warning, so setting it without running the script removes the protection. With the probe off, prod falls back to requiring the acknowledgement, which is the operator’s word and not a check. The script needs the iptables backend, and public IPv6 destinations are not filtered (docs/security.md, Network).

On a host where the script has run, software that ignores the proxy variables gets no network beyond the proxy. That is a cost for some tools, and it is also the intended failure mode.

Limits

The current limits of the allowlist in Sandfort 0.1.0:

  • Entries are host names, leading-dot domains and CIDR ranges. An IP address is reachable only through a CIDR entry, a host name never matches a CIDR entry, and a name that matches no host or domain entry is refused before it is resolved. There are no other wildcards.
  • The list can be replaced on a running sandbox only if the sandbox was created with a non-empty list and a current credential. It cannot be removed. A sandbox created without an allowlist or with an empty one cannot take one, and a legacy credential (policy generation 0) needs a reset first. A change takes about 5 seconds for new connections and about 7 seconds for open tunnels with the defaults, and longer when the proxy cannot reach the policy route.
  • Allowed ports are one list for the whole node (SANDFORT_EGRESS_ALLOWED_PORTS, default 443,80), not per sandbox and not per entry. A CIDR entry carries no port.
  • Jobs mode accepts an allowlisted create, but only on nodes that report the egress stack. Sandbox reset is not available in jobs mode, so the egress token is not refreshed there. An allowlisted jobs-mode sandbox that outlives the token loses egress. A PATCH still works in jobs mode.
  • The egress token has a lifetime (7 days by default, SANDFORT_EGRESS_TOKEN_TTL_S, shortened to the auto-delete horizon plus one day when one is set). A sandbox that outlives its token loses proxy access. An inline-mode reset mints a fresh token.
  • The tunnel cap and the DNS sink apply only to sandboxes on an allowlist. A sandbox on the open network has neither a limit on concurrent outbound connections nor the sink.
  • The network is open by default. A create with neither an allowlist nor block_all reaches the public internet unless the operator sets SANDFORT_DEFAULT_BLOCK_NETWORK or SANDFORT_ENFORCE_BLOCK_NETWORK. Name an allowlist or block_all in the create call instead of relying on the default.
  • Allowlisted sandboxes bypass the warm pool.
  • The proxy checks the name or address in the CONNECT request. It is not a firewall and not full egress control. It does not compare the TLS server name with the CONNECT name, so a client can send a different name inside an allowed tunnel.
  • The allowlist does not change the isolation boundary. The container tier shares the host kernel, and gvisor is a user-space kernel, not a hardware boundary. The microvm tier (Kata Containers) needs KVM. A Firecracker driver exists only as a skeleton and is not offered.

The gate script examples/gate8.py runs this path against real Docker: an allowed host is fetched through the proxy, a fetch of an unlisted host fails, and so does a fetch with a wrong proxy password. The script checks that those fetches exit non-zero, not which status the proxy returned (403 and 407, from src/sandfort/egress/proxy.py). It does not exercise direct IP connections, the metadata address or software that ignores the proxy, and it does not run the Linux host chain. examples/gate11.py covers pinned resolution and the DNS sink: two fetches inside the pin window cause one name lookup, the sink answers udp and tcp queries with REFUSED, and a container-tier sandbox cannot resolve a public name on its own. Its host-dependent steps are skipped, and reported as skipped, without root or a Linux Docker host. It runs its own server and proxy, so it does not test a deployed service. Runtime changes of the list, CIDR entries and jobs mode are covered by unit and integration tests in tests/, not by a gate script. For the tiers themselves, see the earlier article Run the code your agent writes on your own hosts, and the comparison page for other ways to run sandboxes on your own hardware.
