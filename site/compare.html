Sandfort vs E2B vs Daytona vs OpenSandbox: running sandboxes on your own hardware

This page compares four ways to run sandboxes for AI-generated code, with a focus on what each project says about running on your own hardware. It is written by the Sandfort maintainer, so read it with that in mind: every statement about another project has a source link and the date we checked it, and Sandfort claims are drawn from the repository files listed under the table. Where we did not check something, the cell says so. We do not compare prices, speed or “which is better”. You may already use one of these projects.

Facts about other projects go out of date. Check dates are in the Sources section below. If a date is more than a few weeks old, treat the cell as a lead, not a fact.

E2B verified 2026-11-22; first checked 2026-11-10

  • [E1] E2B Embed runs the full stack on one machine: per its README, one node holds the complete E2B runtime, deployed with Docker Compose on a Linux machine you already have. The same package exists as Terraform modules for GCP, AWS and Azure and as a Kubernetes manifest (kubectl apply -k, on a node in an existing cluster), but each of them sets up a single node. The README states that no E2B account and no license key are needed, that Embed answers over HTTP at the machine’s own address without TLS of its own, and that it needs hardware virtualization; the enterprise page lists Linux x86-64 with KVM as the requirement. Azure was added on 2026-10-12 per the changelog. The enterprise page still lists Terraform install for AWS and GCP only; the README and changelog include Azure. https://github.com/e2b-dev/runtime/blob/main/embed/README.mdhttps://e2b.dev/enterprisehttps://docs.e2b.dev/changelog.md
  • [E2] The runtime (control-plane API, per-node orchestrator that drives Firecracker, in-VM agent, edge router, template builder) lives in e2b-dev/runtime; the earlier e2b-dev/infra URL redirects there (HTTP 301, checked 2026-11-22). License: Apache-2.0 (GitHub API: apache-2.0; repository not archived). The repository describes one Firecracker microVM per sandbox. https://github.com/e2b-dev/runtimehttps://api.github.com/repos/e2b-dev/runtime

The BYOC page describes it as a managed deployment in your account rather than self-hosting, available on AWS, Google Cloud and Azure; the enterprise page says it is in production on AWS and GCP. The enterprise page also lists a Private cloud option (control plane and data plane inside the customer boundary) as in development, next to E2B Embed as available. We have not established whether the one-node limit belongs to the product or only to the packages. https://docs.e2b.dev/byoc.mdhttps://e2b.dev/enterprise

OpenSandbox verified 2026-11-22; first checked 2026-11-11; README, ROADMAP and guides read as raw files

The project moves fast, so re-check before relying on a cell.

  • [O1] Repository opensandbox-group/OpenSandbox (the older alibaba/OpenSandbox URL redirects to it). License Apache-2.0 (GitHub API). README: “Start locally with Docker and deploy on Kubernetes through a unified sandbox API”; “Docker (required for local execution)”; SDKs for “Python, Java/Kotlin, TypeScript/JavaScript, C#/.NET, or Go”. Their secure-container guide lists runc (default), gVisor, Kata (QEMU), Kata (Firecracker) and Kata (Cloud Hypervisor) as runtimes; the README’s separate Fast Sandbox runtime on Kubernetes uses Firecracker. https://github.com/opensandbox-group/OpenSandboxhttps://github.com/opensandbox-group/OpenSandbox/blob/main/README.mdhttps://github.com/opensandbox-group/OpenSandbox/blob/main/docs/guides/secure-container.mdhttps://api.github.com/repos/opensandbox-group/OpenSandbox
  • [O2] Multi-tenancy guide: tenants get dedicated API keys and are isolated per Kubernetes namespace; it requires the Kubernetes runtime and states “If runtime.type = "docker" is configured and tenants are enabled, the server refuses to start with a fatal error.” The ROADMAP lists “Agent in-sandbox audit trail” as Planned (records of agent actions inside sandboxes: command execution, file operations, network access) and “eBPF in-sandbox observation” as Implementing (optional, writes a local rotating JSONL audit file). That planned trail covers actions inside sandboxes, so it is not the same thing as Sandfort’s per-org audit chain of API operations. Whether OpenSandbox has a control-plane audit log, we did not check. https://github.com/opensandbox-group/OpenSandbox/blob/main/docs/guides/multi-tenancy.mdhttps://github.com/opensandbox-group/OpenSandbox/blob/main/ROADMAP.md

What the facts above say, by requirement

  • You need a hardware-virtualization boundary for every sandbox in production. E2B’s runtime isolates each sandbox in a Firecracker microVM [E2]. Sandfort always has the container tier; gvisor and microvm are offered only when the operator maps those runtimes in SANDFORT_ISOLATION_RUNTIMES (the hosted beta offers all three), and the microvm tier is Kata Containers behind the same Docker driver and needs KVM. If microVM isolation for all production sandboxes is a requirement, Sandfort does not meet it today.
  • You want to run on a plain Docker host, with governance in the same package. Sandfort’s container tier needs only a Docker daemon (gvisor also needs the runsc runtime), and organizations, scoped keys, roles, quotas, metering and a verifiable audit chain are part of the same server; the chain is tamper-evident only when SANDFORT_AUDIT_CHAIN_KEY is set. OpenSandbox also starts from plain Docker [O1]; per its documentation its per-tenant API keys require Kubernetes, and its in-sandbox agent audit trail is planned [O2]. Re-check that before relying on it, and note that their planned audit trail covers actions inside sandboxes, not API operations, so the two are not like-for-like.
  • You want an Apache-2.0 server. E2B’s runtime and OpenSandbox are Apache-2.0 [E2], [O1]. Sandfort’s server is source-available under FSL-1.1-Apache-2.0: self-hosting and changes are permitted, a competing commercial service is not, and each version becomes Apache-2.0 two years after release.
  • You want a vendor-operated installation in your cloud account. E2B offers BYOC on its Enterprise plan [E3]; Daytona describes BYOC [D3]. Sandfort has no such offering: production is self-hosted by you. The hosted beta is an invite-only, shared evaluation instance: no SLA, not for production secrets or sensitive data, and it may be upgraded with downtime.
  • You need a mature, referenced product. Sandfort is 0.1.0 (pre-1.0 beta) with no production references and no certifications.

How we keep this page honest

  • Each cell about another project has a link and a check date. We re-read each page before publishing and update the date.
  • If you see a cell that is wrong or stale, write to office@sandfort.dev. Corrections are reviewed on a best-effort basis; when a cell changes, its check date is updated.
  • We do not compare prices, because Sandfort has no published prices and we will not guess at anyone else’s.
  • Documentation pages for E2B and Daytona were read through a fetch tool that returns a summary, not verbatim text, so their statements are paraphrased here, not quoted. GitHub API fields and raw files (Daytona LICENSE, the OpenSandbox README, ROADMAP and guides) were read directly and may be quoted. Read the original before you rely on a cell.
