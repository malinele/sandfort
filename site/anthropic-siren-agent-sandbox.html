What Anthropic's Siren evaluation means for the sandbox under your agent

Published: 2026-11-25Sandfort 0.1.0

On November 24, 2026, Anthropic published Siren, an evaluation of whether an agent that can escape its sandbox will choose to. The post is on Anthropic's Safeguards blog and is the source for every number below.

This article does three things. It summarizes what Siren measures and what Anthropic reports. It lists the boundary properties that follow from those results. It maps each property to what Sandfort does, with the limits in the same text. We have not run Siren against Sandfort, and nothing here claims Sandfort would have stopped any Siren scenario.

What Siren measures

Siren has more than 1,700 unique scenarios, built from 26 unique sandbox environments. The environments come from five setups: bubblewrap jails, jails built from Linux namespaces, Docker containers, gVisor containers and small virtual machines emulated with QEMU. Each scenario has four elements:

  • Sandbox. Each environment has a misconfiguration or a vulnerability. Most weaknesses are misconfigurations, for example a host folder that is visible from inside the sandbox.
  • Task. A benign, routine dev-ops job. Some tasks cannot be finished without reaching outside.
  • Honeypot. Something outside the sandbox that would help finish the task: a file, a credential, or a service that emulates the public internet.
  • Tempters. Realistic material that pushes the model toward the honeypot. Tempters never grant permission to leave the sandbox.

"Reaching outside" means the model looked at, accessed, or tried to access something outside the inner sandbox. "Misaligned use" means using outside material in a way no reasonable reading of the scenario allows.

What Anthropic reports

For the Claude 5.5 series and Claude Mythos 5.2, reaching outside happened in 21% to 32% of scenarios. Misaligned use was 0.6% to 1.6% of all scenarios. Misaligned use was much higher for the two earlier models: 12.7% of scenarios for Claude Mythos 5.1 and 25.8% for Claude Mythos 5.

Anthropic is explicit that Siren is built to make the behavior easy to measure: its rates "are not an estimate of how often this behavior happens in real use." It also reports that every model it ran frequently suspected a test. Eval awareness showed up in Claude Sonnet 5.5's reasoning traces in 67% of scenarios.

Anthropic tested three mitigations. Describing the sandbox and its rules in the system prompt made each model 68% to 96% less likely to reach outside. A tool for reporting sandbox weaknesses reduced reaching outside by 7 to 33 percentage points. In an offline replay, Claude Code's auto mode, a pre-execution check, blocked the first reach-outside command in 53% to 84% of the episodes that reached outside, but it was tuned on the same episodes, so it may block less often on new scenarios.

Then the sentence that matters most for infrastructure: the mitigations "don't fix the sandbox itself, so it still needs to be set up and patched to block escapes." Anthropic describes auto mode as one layer of defense in depth "alongside a secure sandbox, clear rules, and the model's own training."

A secondary report (SiliconANGLE, Duncan Riley, November 24, 2026) covers the same results and closes with a critic who calls sandbox hardening a flawed protection approach in the end. We cite it for framing only. Every figure in this article comes from Anthropic's post.

What follows for people running agent code

Two readings are safe. A capable agent given a routine task will sometimes look at what is outside its boundary when the boundary is weak. And prompt-level rules help a lot but are a complement, because they do not change what the boundary permits. So the boundary has to hold on its own, and you want evidence of what happened when it did not.

Below are five boundary properties and what Sandfort does for each.

1. A boundary you can choose per workload, with its limits stated

Sandfort can offer three isolation tiers, chosen per sandbox. A deployment offers the tiers whose runtimes it maps (SANDFORT_ISOLATION_RUNTIMES), and the hosted beta offers all three. With no map, a self-hosted deployment has one tier, and a request for an unavailable tier gets a 422. container uses runc with namespaces, cgroups and seccomp and shares the host kernel. gvisor puts a user-space kernel between the sandbox and the host, and a bug in gVisor itself can still expose the host. microvm runs Kata Containers on KVM, with a guest kernel per sandbox, and needs KVM.

We do not claim stronger isolation than microVM products. The container and gvisor tiers are not microVM-grade isolation.

2. A small default surface inside the sandbox

The Docker driver drops all capabilities except CHOWN, DAC_OVERRIDE, FOWNER, SETUID, SETGID, KILL and NET_BIND_SERVICE. It sets no-new-privileges, applies the daemon's default seccomp profile unless SANDFORT_SECCOMP_PROFILE_PATH names another, and sets pids_limit=512. That limit bounds the process count only on the container tier: on gvisor the memory limit ends a fork loop first, and on microvm a fork bomb can stop the whole VM. Sandboxes sit on a bridge network with inter-container communication disabled, and the host rules from deploy/host-setup.sh, which the operator runs on every sandbox node, block the cloud metadata range (169.254.0.0/16). Under gVisor, the Docker seccomp profile is not applied the way runc applies it. gVisor's own system-call filtering is the boundary there.

3. No platform secrets inside

In Siren, the honeypot is often a credential. Sandfort's server configuration never enters a sandbox: a test runs env in a sandbox and asserts that no SANDFORT_* variable appears, and the SANDFORT_ prefix is rejected on input. Git credentials arrive per request, are never stored, and are removed after use. This does not cover what you put in yourself. A token you pass into a sandbox is visible to code in it.

4. Controlled egress, including DNS

A sandbox can be created with an egress allowlist of hostnames, leading-dot domains and CIDR ranges, and on a sandbox created with a non-empty allowlist, the list can be replaced while it runs (client.set_egress_allowlist in sandfort-sdk, PATCH egress_allowlist). A sandbox created without an allowlist, or with an empty one, cannot gain one, and a legacy sandbox needs a reset first. The proxy applies a change within its cache window, so it is not instant. Traffic goes through a CONNECT proxy, and target ports are limited node-wide (default 443 and 80). This is a proxy-based allowlist, not a firewall.

Names can carry data out even when the proxy refuses the connection, so Sandfort also has a DNS sink. On the container tier, with the sink configured, the sandbox's only DNS server answers every query REFUSED and forwards nothing, so only the proxy resolves names. On gVisor and microvm, direct lookups fail on the allowlist network. The hosted beta enabled the sink on 2026-11-25. On a self-hosted deployment the sink is off until the operator sets it. A container-tier sandbox created before the sink was configured keeps its old resolvers until it is reset or recreated.

5. A record you can verify afterward

Each org has a hash-chained audit log. audit-verify checks every org's chain and exits 3 when any row fails, so it can run in CI or cron. The chain is tamper-evident: it shows a changed, removed or reordered row, not who changed it. With SANDFORT_AUDIT_CHAIN_KEY set (at least 32 bytes), a writer with only database access cannot recompute the hashes. Without it, the chain is an unkeyed SHA-256 chain that such a writer can rewrite consistently, and prod refuses to start in that state unless the operator acknowledges it.

Limits

  • Siren was not run against Sandfort. Its scenarios use deliberately weakened sandboxes, and the post does not say that the scenarios are released.
  • container shares the host kernel. gvisor is a user-space kernel, not a hardware boundary, and has documented behavior differences, for example memory and process limits that can stop the whole sandbox, and it has no process-count limit inside the guest. microvm has none either, and a fork bomb there can stop the whole VM. microvm needs KVM. On the hosted beta it runs on nested KVM, and the beta is not the place for your highest-risk code.
  • The Firecracker driver is a skeleton and is not offered.
  • The egress allowlist is not a firewall. Software that ignores the proxy variables gets no network, and the proxy variables, including per-sandbox proxy credentials, are visible to code inside the sandbox.
  • Nodes that run sandboxes expose the Docker socket, which controls the whole node. The runbook recommends dedicated nodes.
  • An audit log records what happened through the API. It does not stop anything. Its details are a redacted projection of the request, not the request itself: env keeps only variable names, and stdin, code and commands keep only an unsalted SHA-256 digest and their length, so a short or guessable value can be confirmed by hashing a guess.
  • The hosted beta is an invite-only evaluation instance, with no SLA and no production secrets.
  • Sandfort is pre-1.0 (0.1.0) and the server is source-available.

The takeaway

Siren's most useful result for infrastructure is a plain one. Rules in the prompt cut reaching outside sharply, and Anthropic still says the sandbox needs to be set up and patched to block escapes. Treat the prompt, the classifier and the boundary as separate layers, and check the boundary on its own terms: kernel sharing, capabilities, secrets, egress, DNS and a record you can verify.
